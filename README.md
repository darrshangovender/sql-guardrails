> A small library that takes LLM-generated SQL, parses it, and rejects anything destructive, expensive, or out-of-allowlist. Use it in front of any "natural language to SQL" pipeline.

**Why this exists.** Every NL→SQL system has the same problem: the LLM will eventually generate `DELETE FROM users` or `DROP TABLE orders`. Naive string-filtering (regex for "DROP") fails on cleverly nested CTEs. AST parsing is the only safe approach.

This is the extracted, reusable guardrail layer from InsightEngine — production-tested on a multi-table Postgres warehouse with zero destructive incidents.

---

## What it does

```python
from sql_guardrails import Guard, Policy

policy = Policy(
    allow=["SELECT"],
    deny=["DROP", "DELETE", "UPDATE", "INSERT", "TRUNCATE", "ALTER", "GRANT"],
    max_joins=5,
    max_estimated_cost=10000,    # via EXPLAIN
    timeout_seconds=8,
)
guard = Guard(policy, connection=postgres_conn)

result = guard.check(llm_generated_sql)
if not result.safe:
    raise UnsafeSQLError(result.reason)
```

Features:

- **AST parsing via sqlglot** — catches destructive ops hidden in CTEs, subqueries, UNIONs
- **EXPLAIN cost check** — rejects queries whose planner estimate exceeds threshold
- **Join count limit** — defends against accidental cartesian explosions
- **Allowlist of functions/keywords** — strict by default
- **Statement timeout** — set on the executing connection, not just on the guard
- **Audit log** — every rejection logged with reason + raw SQL for review

## Why this is its own library

You'll write the same guardrails for every NL→SQL project you do. Extracting them as a single, tested library means:

- One audit (security review) covers every project using it
- Bug-fixes propagate
- New attack vectors get one fix, applied everywhere

## Threat model

The library defends against:

1. **Destructive operations** generated by the LLM (most common, easiest to catch)
2. **Resource exhaustion** — runaway queries from missing predicates (`SELECT * FROM huge_fact_table`)
3. **Cross-tenant data leaks** — combined with the SQL connection's row-level security policies, the guard verifies query structure can't bypass RLS
4. **Schema discovery** — by default, denies `pg_catalog` and `information_schema` access; opt-in if your use case needs it

What it does **not** defend against:
- LLM exfiltrating data via answer text (a different problem — output filtering)
- Side-channel attacks via timing
- Compromised database credentials

## Eval

A red-team test set ships with the repo: ~150 adversarial SQL strings (some from real LLM outputs, some hand-crafted) labelled as `safe` or `unsafe`. The guard must achieve 100% block rate on unsafe and < 1% false-positive rate on safe.
